# Quick deploy Minio, Polaris & Trino

This project provides a sample custom docker-compose.yml file and a setup.sh to quickly spin up Minio, the Polaris REST catalog and a Trino query engine on the same Linux server. The objective is to allow quick deployment of an Iceberg lakehouse stack, ready for lab testing in Dataiku with minimal user intervention:

```
Dataiku Iceberg connection --REST--> Polaris (dataiku_catalog) --> Postgres (catalog metadata)
        |                                   ^
        +--S3 connection--> Minio (bucket "dataiku")
                                            |
Dataiku Trino connection --JDBC--> Trino (catalog "iceberg", REST, warehouse=dataiku_catalog)
                                            +--S3--> Minio (same bucket)
```

Dataiku (Iceberg connection) and Trino read and write the same Iceberg tables.

## Files

1.  **docker-compose.yml**: Deploys and configures the following containers - 
    - Minio container with service listening on port 9000 and UI on port 9001, default credentials(minioadmin/minioadmin) and default bucket(dataiku). 
    - Postgres database (polaris) to support Polaris REST catalog (internal to the compose network, port 5432 is not published).
    - Polaris REST catalog container with API endpoint listening on port 8181 and management on port 8182, with connectivities configured to the Postgres database and Minio service, and a transient polaris-setup-worker to run setup.sh to create the following resources in the catalog.
    - Trino (single node) listening on port 8080 (override with `TRINO_PORT`), with an `iceberg` catalog backed by Polaris and Minio, and a `hive` catalog used only as a staging area for Dataiku's Automatic fast-write. It starts after the setup worker has finished and has a healthcheck.
    - A transient trino-init container that, once Trino is healthy, creates the `hive.staging` schema used by fast-write (idempotent, re-created on every `up`).

2.  **setup.sh**: Executed by transient setup worker to provision the Polaris REST catalog. The key resources created 
    - warehouse/catalog = dataiku_catalog
    - principal user = dataiku (with CLIENT_ID and CLIENT_SECRET written into polaris_creds.env) with associated roles 
    - namespace = dataiku  

3.  **create-polaris-schema.sql**: Mounted into the Postgres container and run on first init to create the `polaris_schema` schema, which Polaris requires but does not create itself.

4.  **trino/catalog/iceberg.properties**: Trino catalog definition: Iceberg connector, REST catalog at `http://polaris:8181/api/catalog`, warehouse `dataiku_catalog`, OAuth2 with scope `PRINCIPAL_ROLE:ALL`, and Minio (`http://minio:9000`, path-style) as storage. The OAuth2 credential is injected from the environment, never stored in this file.

5.  **trino/catalog/hive.properties**: Trino catalog definition for fast-write staging: Hive connector with the file metastore kept in Minio (`s3://dataiku/hive-metastore/`, so no Hive Metastore container is needed) and Minio as storage. It holds no real data: Trino only creates temporary external tables here over the Parquet files DSS stages in `s3://dataiku/trino-staging/`. Trino loads catalog files at startup, so its name (`hive`) is what you enter as "Catalog for fast-load" in Dataiku.

6.  **trino/entrypoint.sh**: Trino container entrypoint. Reads `polaris_creds.env` (so Trino always uses the freshly generated credentials), exports them as `POLARIS_CREDENTIAL`, applies the heap cap `TRINO_HEAP` to a copy of the image's `jvm.config`, then starts Trino with the image's default command.

7.  **polaris_creds.env**: Generated by setup.sh in this folder with the Polaris REST catalog user credentials (not committed to git). It is only written when the `dataiku` principal is first created; re-running keeps the existing file.

Note: no volumes are used, so all Minio data and catalog metadata are discarded on `docker compose down`. The setup is safe to re-run against a running stack.

## Setup Instructions with Dataiku

You can either run this on a standalone Linux server with network connectivity to the DSS instance OR simply run them on the DSS instance. Ensure docker compose (v2) is installed on the server:

*  Clone this repo (or place docker-compose.yml, setup.sh, create-polaris-schema.sql and the `trino/` folder in the same folder) and run `docker compose up -d`. The credentials are written to `polaris_creds.env` in that folder. The first run pulls several images and takes a few minutes.
*  If a default port is already taken on the host, override it by exporting the variable(s) below (or putting them in a `.env` file next to docker-compose.yml) before `docker compose up -d`:

    | Variable | Service | Default |
    |---|---|---|
    | `MINIO_API_PORT` | Minio S3 API | 9000 |
    | `MINIO_CONSOLE_PORT` | Minio UI | 9001 |
    | `POLARIS_API_PORT` | Polaris REST API | 8181 |
    | `POLARIS_MGMT_PORT` | Polaris management/health | 8182 |
    | `TRINO_PORT` | Trino | 8080 |

    e.g. `MINIO_API_PORT=19000 POLARIS_API_PORT=18181 docker compose up -d`. Use the same ports in the Dataiku connections below. Postgres is not published, so it needs no port.
*  Take note of your primary IP address [HOST_IP] of the host machine. In cloud environment, it is typically in 10.x.x.x address. This will be the IP address the Minio, Polaris and Trino services listening on.
*  Verify the stack:
    ```bash
    docker compose ps -a                                   # one-shot containers show Exited (0); the rest Up
    docker compose logs polaris-setup-worker | tail -5     # "Setup complete!"
    docker exec -it trino trino --execute "SHOW SCHEMAS FROM iceberg"   # lists "dataiku"
    ```

### Creating the connections

Create three connections in Dataiku (Administration > Connections > New connection): an **S3** connection to Minio, an **Iceberg** connection to Polaris, and, optionally, a **Trino** connection. Create the S3 connection first, then the Iceberg connection, then Trino.

*  **Connection 1 of 3 - S3 connection (to Minio).** At Dataiku instance, create a new **S3** connection and provide the following parameters:
    #### Connection
    - Credentials: AWS keypair
    - Access key: minioadmin
    - Secret key: minioadmin
    - Region/Endpoint: http://[HOST_IP]:[MINIO_API_PORT] (default 9000)
    #### Path restrictions
    - Bucket: dataiku
    #### Advanced
    - Use path style: CHECKED

*  **Connection 2 of 3 - Iceberg connection (to Polaris).** At Dataiku instance, create a new **Iceberg** connection and provide the following parameters:
    #### Connection
    - Catalog type: REST
    - URI: http://[HOST_IP]:[POLARIS_API_PORT]/api/catalog (default 8181)
    - Warehouse: dataiku_catalog
    - Authentication type: User/Password
        - User: [CLIENT_ID]
        - Password: [CLIENT_SECRET]
    #### Properties
    - Catalog properties: scope -> PRINCIPAL_ROLE:ALL
    #### Namespaces
    - Default namespace: dataiku
    #### Rules for new datasets
    - namespace: dataiku
    #### Custom properties
    - Catalog name: dataiku_catalog
    - (Optional, only if you also intend to use Trino with these Iceberg datasets) Link the Iceberg connection to Trino. Create the Trino connection below first (or come back to this step afterwards), then set:
        - Associated Trino conn.: the exact name of your Dataiku Trino connection (e.g. `local_trino`)
        - Associated Trino catalog: `iceberg` (the Trino catalog defined by `trino/catalog/iceberg.properties`, not the Polaris catalog name `dataiku_catalog`)

        Leave "Is Athena connection" unchecked. With both values set, Dataiku knows which Trino connection and catalog expose the same tables, so Trino can be used as an engine on Iceberg datasets.

*  **Connection 3 of 3 (optional) - Trino connection.** To query the same Iceberg tables with Trino, create a new **Trino** connection (a native connection type in recent DSS versions) and provide the following parameters:
    #### Basic params
    - Host: [HOST_IP] (or `localhost` when DSS runs on the same machine as the containers)
    - Port: 8080 (or your `TRINO_PORT`)
    - Catalog: iceberg
    - Auth type: User/Password
        - User: dataiku (any value; Trino has no authentication configured)
        - Password: (empty)
    #### Advanced params
    - Driver to use: Dataiku-managed
    - Automatic fast-write (recommended): checked, with the values below. This is what makes large loads from other engines into Trino fast; see "Trino Automatic fast-write" for how it works.
        - Automatic fast-write connection: the exact name of the S3 connection to Minio created in Connection 1 (e.g. `local_minio`)
        - Path in connection: `trino-staging`
        - Catalog for fast-load: `hive`
        - Schema for fast-load: `staging`
        - Leave "Fetch size" empty
    #### Rules for new datasets
    - Catalog: iceberg
    - Schema: dataiku
    - Table prefix: `${projectKey}_` (default)

    Naming: the Trino catalog `iceberg` is defined by `trino/catalog/iceberg.properties` and points at the Polaris catalog `dataiku_catalog`; the Polaris namespace `dataiku` is the Trino schema. A table is addressed as `iceberg.dataiku.<table>`. Tables written through the Dataiku Iceberg connection appear in Trino and vice versa. Trino lowercases table names.

*  To tear down setup, run `docker compose down`

## Loading data: which path to use

| Goal | Recommended path |
|---|---|
| Bulk load data into Iceberg | Write to a dataset on the **Iceberg connection** (Dataiku writes Parquet straight to Minio; Polaris only commits metadata) |
| Transform data already in Trino | A recipe whose input and output are both on the **Trino connection** runs in-database (`INSERT ... SELECT`) |
| Small outputs from another engine into Trino | Works through plain JDBC `INSERT` (DSS engine), e.g. a Sample/Filter recipe with a few rows |
| Large outputs from another engine into Trino | Enable **Automatic fast-write** on the Trino connection (see below). Without it DSS streams rows through JDBC `INSERT` batches, which Trino handles poorly (an initial 29k-row sync hung for minutes); in that case write to the Iceberg connection instead |

### Trino "Automatic fast-write"

For large outputs from other engines into Trino, enable "Automatic fast-write" on the Trino connection (Advanced params).

**How it works**

1. DSS writes the rows as Parquet files to Minio, under `s3://dataiku/trino-staging/tmp.<id>/`, using the S3 connection.
2. Trino creates a temporary external table over those files in the `hive` catalog (`hive.staging.<temp name>`, `external_location=...`).
3. Trino copies the rows into the target Iceberg table (`INSERT INTO iceberg.dataiku.<table> SELECT ... FROM hive.staging.<temp name>`).
4. The temporary table is dropped and DSS deletes the staged files.

This needs a Hive-connector catalog because the Iceberg connector cannot create tables over arbitrary S3 locations. It is provided by `trino/catalog/hive.properties`, with table definitions in Trino's file metastore stored in Minio (no Hive Metastore container). No new bucket or folder needs creating: `trino-staging/` and `hive-metastore/` are prefixes inside the existing `dataiku` bucket and appear when first written. The `trino-init` container creates the `hive.staging` schema on every `up`.

**Setup**

1. Bring the stack up as usual (`docker compose up -d`). Pull the latest repo first (`git pull`) if you cloned it before fast-write was added; the `trino` container is recreated with the new `hive` catalog.
2. Verify the staging catalog and schema exist:
    ```bash
    docker exec -it trino trino --execute "SHOW CATALOGS"                # lists "hive" next to "iceberg"
    docker exec -it trino trino --execute "SHOW SCHEMAS FROM hive"       # lists "staging"
    ```
   (A stray `ppp` before the output is a harmless terminal artifact of `docker exec -it`; use `docker exec -i` to avoid it.)
3. On the Dataiku Trino connection (Advanced params), set:

    | Field | Value |
    |---|---|
    | Automatic fast-write | checked |
    | Automatic fast-write connection | the name of your Dataiku S3 connection to Minio (e.g. `local_minio`) |
    | Path in connection | `trino-staging` |
    | Catalog for fast-load | `hive` |
    | Schema for fast-load | `staging` |

   "Catalog for fast-load" must be set explicitly: if left empty DSS uses the target table's catalog (`iceberg`), which does not allow external locations.

**Verify it is used.** Run a code recipe or a DSS-engine Sync from a non-Trino dataset into a Trino dataset, then check the job log. A fast-write run shows `Starting Cloud->Trino`, a `CREATE TABLE "hive"."staging"...external_location=...` statement, an `INSERT INTO "iceberg"."dataiku"... SELECT ... FROM "hive"."staging"...`, a `DROP TABLE "hive"."staging"...` and `Auto-fast-path: complete`. A plain-JDBC run shows `Executing SQL insert batch` lines instead. You can also list recent statements on the Trino side:
```bash
docker exec -i trino trino --execute "SELECT query, state FROM system.runtime.queries WHERE query LIKE '%staging%' ORDER BY created DESC LIMIT 10"
```

**Notes**

- Fast-write only applies when data is loaded into Trino from outside (code recipes, DSS-engine Sync, etc.). Recipes whose input and output are both on Trino run in-database and do not use it.
- Staged files are deleted after each run, so `trino-staging/` is normally empty between runs. A job that is killed mid-run can leave a `tmp.<id>/` folder behind; it is safe to delete.
- The DSS log line `Commit doesn't work on this Trino connection: Connection is in auto-commit mode` is harmless.
- Validated end to end with DSS 14.4.1 (Dataiku-managed Trino JDBC driver 463) and Trino 484: a DSS-engine Sync of a Hive table into an Iceberg-backed Trino dataset.
- The `hive` catalog and `hive.staging` schema are not persisted: like everything else here they are lost on `docker compose down`, and recreated by the next `up`.

## Additional Notes

**No persistence:** This setup is for lab use and defines no Docker volumes. Minio objects (the `dataiku` bucket and all Iceberg data) and the Polaris catalog metadata (Postgres) are lost when the containers are removed with `docker compose down`. After bringing the stack back up, setup.sh generates new Dataiku credentials, so update the Dataiku Iceberg connection accordingly (the Trino connection needs no change).

The polaris-setup-worker spins up on `network_mode=host` in order to be on the same network as the host machine and setup.sh will then try to retrieve the host's machine IP address in order to configure the Polaris REST catalog to connect with the Minio service also listening on the same IP address. This process should work fine in most situations but not thoroughly validated.

If the wrong IP is detected, export `HOST_IP=<ip>` before running `docker compose up -d` to override it.

## Resource limits (shared host)

These containers may share a host with a Dataiku DSS node, so every long-running service has a memory cap and `restart: unless-stopped`. Defaults (override by exporting before `docker compose up -d`):

| Service | Container limit | JVM heap | Variables |
|---|---|---|---|
| Polaris | 3g | 1536m (+256m direct) | `POLARIS_MEM_LIMIT`, `POLARIS_HEAP`, `POLARIS_DIRECT_MEM` |
| Trino | 4g | 3G | `TRINO_MEM_LIMIT`, `TRINO_HEAP` |
| Postgres | 512m | n/a | `POLARIS_DB_MEM_LIMIT` |
| Minio | 1g | n/a | `MINIO_MEM_LIMIT` |

Heap is kept below the container limit so the JVM fails or garbage-collects before the kernel OOM-kills the container. If a container is killed, Docker restarts it; catalog state survives (it is in Postgres). Verify the caps took effect with `docker stats --no-stream`.

Trino is pinned to `trinodb/trino:484` and Polaris (server and admin tool) to `1.8.0`, the versions validated on the lab host. To see what a running Polaris is: `docker compose logs polaris --no-color | grep -a "polaris-server"`.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| Trino: `Failed to check namespace 'dataiku'` right after Polaris restarted | Trino holds a token from the previous Polaris process. Restart Trino: `docker compose restart trino`. **If Polaris restarts, also restart Trino** (`docker compose restart polaris trino`). |
| Dataiku dataset creation fails with `Failed to load view ... Read timed out`; `SHOW TABLES FROM iceberg.dataiku` hangs | Polaris is wedged (seen once, at ~14 GiB memory with idle CPU and Postgres). Restart Polaris and Trino as above. Check `docker stats` and `docker compose logs polaris`. |
| Dataiku job to a Trino dataset runs for minutes at "Executing SQL insert batch" | Large JDBC `INSERT` batches. See "Loading data" above; write to the Iceberg connection instead. |
| Trino container exits immediately | `polaris_creds.env` is missing or unreadable. Check `docker compose logs trino` and that `polaris-setup-worker` exited 0. |
| `hive` missing from `SHOW CATALOGS`, or Trino fails to start with a `hive.metastore` error | `trino/catalog/hive.properties` is not mounted or has an error. Run `git pull`, then `docker compose up -d trino` (Trino only loads catalog files at startup) and check `docker compose logs trino`. |
| `hive.staging` schema missing | `trino-init` did not run or failed. Check `docker compose ps -a trino-init` and `docker compose logs trino-init`; it only runs once Trino reports healthy. Re-run with `docker compose up -d`. |
| Dataiku Trino job log shows `Executing SQL insert batch` and no `hive.staging` statements | Fast-write was not used: the recipe may run in-database, or the Trino connection's fast-write fields are unset or unsaved. Check "Catalog for fast-load" is `hive` and "Schema for fast-load" is `staging`. |
| Fast-write job fails creating `hive.staging.*` or reading the staged files | The `hive` catalog cannot reach Minio, or the DSS S3 connection and the path differ. Check `docker compose logs trino`, that the S3 connection allows bucket `dataiku`, and that "Path in connection" is `trino-staging`. |
| Dataiku Iceberg connection stops working after `down`/`up` | New credentials were generated. Copy `CLIENT_ID` / `CLIENT_SECRET` from `polaris_creds.env`. |
| Trino connection lists extra tables (`information_schema`, `system`, `jmx`) | Built-in Trino metadata and example catalogs. Your tables are under `iceberg.dataiku`. |
