# Quick deploy Minio, Polaris & Trino

This project provides a sample custom docker-compose.yml file and a setup.sh to quickly spin up Minio, the Polaris REST catalog and a Trino query engine on the same Linux server. The objective is to allow quick deployment of an Iceberg lakehouse stack, ready for lab testing in Dataiku with minimal user intervention:

```
Dataiku Iceberg connection --REST--> Polaris (dataiku_catalog) --> Postgres (catalog metadata)
        |                                   ^
        +--S3 connection--> Minio (bucket "dataiku")
                                            |
Dataiku Trino connection --JDBC--> Trino (catalog "iceberg", REST, warehouse=dataiku_catalog)
                                            +--S3--> Minio (same bucket)
```

Dataiku (Iceberg connection) and Trino read and write the same Iceberg tables.

## Files

1.  **docker-compose.yml**: Deploys and configures the following containers - 
    - Minio container with service listening on port 9000 and UI on port 9001, default credentials(minioadmin/minioadmin) and default bucket(dataiku). 
    - Postgres database (polaris) to support Polaris REST catalog (internal to the compose network, port 5432 is not published).
    - Polaris REST catalog container with API endpoint listening on port 8181 and management on port 8182, with connectivities configured to the Postgres database and Minio service, and a transient polaris-setup-worker to run setup.sh to create the following resources in the catalog.
    - Trino (single node) listening on port 8080 (override with `TRINO_PORT`), with an `iceberg` catalog backed by Polaris and Minio. It starts after the setup worker has finished.

2.  **setup.sh**: Executed by transient setup worker to provision the Polaris REST catalog. The key resources created 
    - warehouse/catalog = dataiku_catalog
    - principal user = dataiku (with CLIENT_ID and CLIENT_SECRET written into polaris_creds.env) with associated roles 
    - namespace = dataiku  

3.  **create-polaris-schema.sql**: Mounted into the Postgres container and run on first init to create the `polaris_schema` schema, which Polaris requires but does not create itself.

4.  **trino/catalog/iceberg.properties**: Trino catalog definition: Iceberg connector, REST catalog at `http://polaris:8181/api/catalog`, warehouse `dataiku_catalog`, OAuth2 with scope `PRINCIPAL_ROLE:ALL`, and Minio (`http://minio:9000`, path-style) as storage. The OAuth2 credential is injected from the environment, never stored in this file.

5.  **trino/entrypoint.sh**: Trino container entrypoint. Reads `polaris_creds.env` (so Trino always uses the freshly generated credentials), exports them as `POLARIS_CREDENTIAL`, applies the heap cap `TRINO_HEAP` to a copy of the image's `jvm.config`, then starts Trino with the image's default command.

6.  **polaris_creds.env**: Generated by setup.sh in this folder with the Polaris REST catalog user credentials (not committed to git). It is only written when the `dataiku` principal is first created; re-running keeps the existing file.

Note: no volumes are used, so all Minio data and catalog metadata are discarded on `docker compose down`. The setup is safe to re-run against a running stack.

## Setup Instructions with Dataiku

You can either run this on a standalone Linux server with network connectivity to the DSS instance OR simply run them on the DSS instance. Ensure docker compose (v2) is installed on the server:

*  Clone this repo (or place docker-compose.yml, setup.sh, create-polaris-schema.sql and the `trino/` folder in the same folder) and run `docker compose up -d`. The credentials are written to `polaris_creds.env` in that folder. The first run pulls several images and takes a few minutes.
*  Take note of your primary IP address [HOST_IP] of the host machine. In cloud environment, it is typically in 10.x.x.x address. This will be the IP address the Minio, Polaris and Trino services listening on.
*  Verify the stack:
    ```bash
    docker compose ps -a                                   # one-shot containers show Exited (0); the rest Up
    docker compose logs polaris-setup-worker | tail -5     # "Setup complete!"
    docker exec -it trino trino --execute "SHOW SCHEMAS FROM iceberg"   # lists "dataiku"
    ```

### Creating the connections

*  At Dataiku instance, create a new S3 connection and provide the following parameters:
    #### Connection
    - Credentials: AWS keypair
    - Access key: minioadmin
    - Secret key: minioadmin
    - Region/Endpoint: http://[HOST_IP]:9000
    #### Path restrictions
    - Bucket: dataiku
    #### Advanced
    - Use path style: CHECKED

*  At Dataiku instance, create a new Iceberg connection and provide the following parameters:
    #### Connection
    - Catalog type: REST
    - URI: http://[HOST_IP]:8181/api/catalog
    - Warehouse: dataiku_catalog
    - Authentication type: User/Password
        - User: [CLIENT_ID]
        - Password: [CLIENT_SECRET]
    #### Properties
    - Catalog properties: scope -> PRINCIPAL_ROLE:ALL
    #### Namespaces
    - Default namespace: dataiku
    #### Rules for new datasets
    - namespace: dataiku
    #### Custom properties
    - Catalog name: dataiku_catalog

*  (Optional) To query the same Iceberg tables with Trino, create a new **Trino** connection (a native connection type in recent DSS versions) and provide the following parameters:
    #### Basic params
    - Host: [HOST_IP] (or `localhost` when DSS runs on the same machine as the containers)
    - Port: 8080 (or your `TRINO_PORT`)
    - Catalog: iceberg
    - Auth type: User/Password
        - User: dataiku (any value; Trino has no authentication configured)
        - Password: (empty)
    #### Advanced params
    - Driver to use: Dataiku-managed
    #### Rules for new datasets
    - Catalog: iceberg
    - Schema: dataiku
    - Table prefix: `${projectKey}_` (default)

    Naming: the Trino catalog `iceberg` is defined by `trino/catalog/iceberg.properties` and points at the Polaris catalog `dataiku_catalog`; the Polaris namespace `dataiku` is the Trino schema. A table is addressed as `iceberg.dataiku.<table>`. Tables written through the Dataiku Iceberg connection appear in Trino and vice versa. Trino lowercases table names.

*  To tear down setup, run `docker compose down`

## Loading data: which path to use

| Goal | Recommended path |
|---|---|
| Bulk load data into Iceberg | Write to a dataset on the **Iceberg connection** (Dataiku writes Parquet straight to Minio; Polaris only commits metadata) |
| Transform data already in Trino | A recipe whose input and output are both on the **Trino connection** runs in-database (`INSERT ... SELECT`) |
| Small outputs from another engine into Trino | Works through plain JDBC `INSERT` (DSS engine), e.g. a Sample/Filter recipe with a few rows |
| Large outputs from another engine into Trino | Avoid: DSS streams rows through JDBC `INSERT` batches, which Trino handles poorly (an initial 29k-row sync hung for minutes). Write to the Iceberg connection instead |

Trino's "Automatic fast-write" is not configured here: it needs a Hive-connector catalog (and a Hive Metastore), which this stack does not include.

## Additional Notes

**No persistence:** This setup is for lab use and defines no Docker volumes. Minio objects (the `dataiku` bucket and all Iceberg data) and the Polaris catalog metadata (Postgres) are lost when the containers are removed with `docker compose down`. After bringing the stack back up, setup.sh generates new Dataiku credentials, so update the Dataiku Iceberg connection accordingly (the Trino connection needs no change).

The polaris-setup-worker spins up on `network_mode=host` in order to be on the same network as the host machine and setup.sh will then try to retrieve the host's machine IP address in order to configure the Polaris REST catalog to connect with the Minio service also listening on the same IP address. This process should work fine in most situations but not thoroughly validated.

If the wrong IP is detected, export `HOST_IP=<ip>` before running `docker compose up -d` to override it.

## Resource limits (shared host)

These containers may share a host with a Dataiku DSS node, so every long-running service has a memory cap and `restart: unless-stopped`. Defaults (override by exporting before `docker compose up -d`):

| Service | Container limit | JVM heap | Variables |
|---|---|---|---|
| Polaris | 3g | 1536m (+256m direct) | `POLARIS_MEM_LIMIT`, `POLARIS_HEAP`, `POLARIS_DIRECT_MEM` |
| Trino | 4g | 3G | `TRINO_MEM_LIMIT`, `TRINO_HEAP` |
| Postgres | 512m | n/a | `POLARIS_DB_MEM_LIMIT` |
| Minio | 1g | n/a | `MINIO_MEM_LIMIT` |

Heap is kept below the container limit so the JVM fails or garbage-collects before the kernel OOM-kills the container. If a container is killed, Docker restarts it; catalog state survives (it is in Postgres). Verify the caps took effect with `docker stats --no-stream`.

Trino is pinned to `trinodb/trino:484` and Polaris (server and admin tool) to `1.8.0`, the versions validated on the lab host. To see what a running Polaris is: `docker compose logs polaris --no-color | grep -a "polaris-server"`.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| Trino: `Failed to check namespace 'dataiku'` right after Polaris restarted | Trino holds a token from the previous Polaris process. Restart Trino: `docker compose restart trino`. **If Polaris restarts, also restart Trino** (`docker compose restart polaris trino`). |
| Dataiku dataset creation fails with `Failed to load view ... Read timed out`; `SHOW TABLES FROM iceberg.dataiku` hangs | Polaris is wedged (seen once, at ~14 GiB memory with idle CPU and Postgres). Restart Polaris and Trino as above. Check `docker stats` and `docker compose logs polaris`. |
| Dataiku job to a Trino dataset runs for minutes at "Executing SQL insert batch" | Large JDBC `INSERT` batches. See "Loading data" above; write to the Iceberg connection instead. |
| Trino container exits immediately | `polaris_creds.env` is missing or unreadable. Check `docker compose logs trino` and that `polaris-setup-worker` exited 0. |
| Dataiku Iceberg connection stops working after `down`/`up` | New credentials were generated. Copy `CLIENT_ID` / `CLIENT_SECRET` from `polaris_creds.env`. |
| Trino connection lists extra tables (`information_schema`, `system`, `jmx`) | Built-in Trino metadata and example catalogs. Your tables are under `iceberg.dataiku`. |
